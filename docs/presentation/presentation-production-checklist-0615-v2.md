## 1. 10분 발표 구조 체크

### 1-1. 0610 PDF 기본 구조 반영 여부

| 블록 | 질문 | 충족 기준 |
|---|---|---|
| Title | 첫 장이 형식 표지가 아니라 프로젝트를 각인하는가? | 프로젝트명, 캐치프레이즈, 키워드가 보인다. |
| 1 sentence | 한 문장 정체가 명확한가? | 관객이 이 문장으로 프로젝트를 기억할 수 있다. |
| Demo teaser | 초반에 무엇을 만들었는지 감이 오는가? | 실제 화면 또는 3분할 미리보기가 있다. |
| Context | 관객이 공감할 출발점이 있는가? | “같은 책, 다른 밑줄” 같은 감각적 진입이 있다. |
| Problem | 기능 부족이 아니라 병목이 보이는가? | 디지털 읽기의 평평함, 흔적의 유실이 보인다. |
| Your Innovation | 새 제안이 무엇인지 보이는가? | HDI -> DHI, 흔적을 AI-readable하게 만드는 전환이 보인다. |
| How | 작동 모델이 보이는가? | 지지고 볶기/흔적/비추기와 4단 시간 구조가 분리된다. |
| development | 실제 만든 것과 과정이 보이는가? | 신호, 촛불, 보드, 맵이 판단의 흐름 안에 있다. |
| Main Demo | 진짜 만들었다와 와우 포인트가 있는가? | 흔적 -> 촛불 -> 보드/맵 장면이 이어진다. |
| Validation | 검증과 리서치가 분리되는가? | Research Grounding과 Next Test가 분리된다. |
| Conclusion | Thank you로 끝나지 않는가? | Recap, Vision, 마지막 질문이 있다. |

### 1-2. 시간 배분 체크

| 구간 | 권장 시간 | 체크 |
|---|---:|---|
| 오프닝/제품 정체 | 0:00-1:05 | 공감과 한 문장이 너무 길어지지 않는가? |
| Context/Problem | 1:05-2:50 | 종이책/디지털 대비가 명확한가? |
| Innovation/How | 2:50-4:25 | 제안과 구조가 데모 전에 잡히는가? |
| Demo | 4:25-6:50 | 60-90초 중심으로 압축 가능한가? |
| 다음 읽기 전/차별화 | 6:50-7:55 | `저녁에 읽으세요`가 후반 회수로 작동하는가? |
| Research/Next Test | 7:55-9:05 | 논문 설명이 길어지지 않는가? |
| Recap/Vision | 9:05-10:00 | 마지막에 디자이너의 관점이 남는가? |

## 2. 첫 장/마지막 장 체크

### 첫 장

- [ ] `Final Presentation`만 있는 표지가 아니다.
- [ ] 프로젝트명 `Layer 2`가 크고 명확하다.
- [ ] 캐치프레이즈가 있다.
- [ ] 핵심 키워드가 있다.
- [ ] 첫인상에서 독서/흔적/두 번째 레이어의 감각이 보인다.

권장:

> Layer 2  
> 책과 나를 함께 깊이 이해하는, 똘똘한 디지털 독서 도구  
> 지지고 볶기 / 흔적 남기기 / 나를 비추기

### 마지막 장

- [ ] `Thank you`만 있지 않다.
- [ ] 4단 구조 Recap이 있다.
- [ ] 구현/비전/다음 질문이 정리된다.
- [ ] Q&A로 넘어가기 좋다.
- [ ] 마지막 장만 봐도 프로젝트가 다시 잡힌다.

권장:

> 읽기 시작 -> 읽기 중 -> 읽기 후 -> 다음 읽기 전  
> 읽기에서 사라지던 흔적을 AI가 읽을 수 있게 만들고, 다시 사람에게 돌려주는 실험  
> 디자이너는 무엇을 읽게 해야 하는가?

## 3. 평가기준 매핑 체크

### 3-1. 커뮤니케이션

- [ ] 처음 보는 사람이 이해할 수 있다.
- [ ] “그래서 뭘 만든 거죠?”가 나오지 않는다.
- [ ] 한 슬라이드에 정보가 과밀하지 않다.
- [ ] 기능들이 모두 자기주장을 하지 않는다.
- [ ] 데모 옆에 단계 타임라인 또는 미니 도식이 있다.
- [ ] 본편과 Appendix가 분리된다.

보완 신호:

- 발표자가 설명해야만 이해되는 슬라이드가 많다.
- 초반 1분 안에 실제 제품 화면이 전혀 보이지 않는다.
- 촛불/보드/맵/리포트가 같은 무게로 보인다.

### 3-2. 노벨티/이노베이션

- [ ] 기존 도구와 다른 점이 보인다.
- [ ] 새로움이 프로젝트 컨텍스트에서 필요한 이유가 보인다.
- [ ] `AI 요약/추천`으로 오해되지 않는다.
- [ ] `흔적을 AI가 읽을 수 있게 한다`가 핵심으로 남는다.
- [ ] HDI -> DHI가 관점 전환으로 보인다.

보완 신호:

- GPT와 뭐가 다른지 모호하다.
- Readwise와 차이가 하이라이트 기능 차이처럼만 보인다.
- 새로움이 기술 기능 추가처럼 보인다.

### 3-3. 프로세스

- [ ] 출발점이 보인다.
- [ ] 바뀐 판단이 보인다.
- [ ] 피드백을 어떻게 해석했는지 보인다.
- [ ] 구현된 것과 남은 것이 분리된다.
- [ ] 과정이 너무 장황하지 않다.

권장 문장 구조:

> 처음에는 A에서 출발했습니다.  
> 만들면서 B가 문제라는 걸 알았습니다.  
> 그래서 C는 유지하고 D는 줄였습니다.  
> 그 결과 지금은 E 구조로 정리했습니다.

### 3-4. 융합 디자인 언어

- [ ] 디자이너의 관심사가 보인다.
- [ ] 인간 감각/인지와 기술 구현이 연결된다.
- [ ] 디자인 판단이 기능과 화면에 반영된다.
- [ ] 마지막 비전이 갑자기 튀어나오지 않는다.
- [ ] “효율 속에서 지워진 부산물”이라는 관점이 읽기 프로젝트와 연결된다.

보완 신호:

- 마지막 매니페스토가 앞 내용과 별개로 보인다.
- 화면은 기능 도구인데 말은 감각/부산물로만 간다.
- 디자이너 소개가 프로젝트와 연결되지 않는다.

### 3-5. 임팩트

- [ ] 제품 밖의 가능성이 보인다.
- [ ] 연구/디자인/개발 커뮤니티 중 어디에 기여할지 상상된다.
- [ ] 오픈소스/엔진/방법론/에이전트 루프 중 하나의 방향이 보인다.
- [ ] 과장과 가능성 사이의 균형이 있다.

Layer 2 가능한 임팩트 문장:

> Layer 2는 독서 앱 하나를 넘어서, 웹 문서 안에서 인간의 어텐션과 마찰이 어떻게 배분되는지 읽는 경량 신호 엔진이 될 수 있습니다.

또는:

> AI가 텍스트만 읽는 것이 아니라, 사람이 텍스트와 관계 맺는 흔적까지 읽게 하는 인터랙션 방법론입니다.

## 4. 데모 체크

### 4-1. 데모 목표

- [ ] 진짜 만들었다가 보인다.
- [ ] 와우 포인트가 있다.
- [ ] 기능 순서 나열이 아니다.
- [ ] 핵심 인터랙션 포인트가 보인다.
- [ ] 로딩/실패 리스크를 줄였다.

### 4-2. Layer 2 데모 필수 장면

| 장면 | 보여줄 것 | 주의 |
|---|---|---|
| 읽기 시작 | 무거운 글을 Layer 2로 가져옴 | 길게 설명하지 않는다. |
| 읽기 중 흔적 | 밑줄, 주석, 머묾, 되돌아읽기 | 점수처럼 보이지 않게 한다. |
| 촛불 | 흔적의 이음새에서 질문 | 주인공처럼 과장하지 않는다. |
| 보드 전환 | 단락 단위로 흔적 보기 | 선생님이 좋다고 한 지점이다. |
| Mental Model Map | 이번 글을 내가 어떻게 읽었는지 | 예쁜 시각화가 아니라 되비춤이다. |
| 다음 읽기 전 | 저녁에 읽으세요 회수 | 구현 완료 추천처럼 말하지 않는다. |

### 4-3. 데모 옆 보조 도식

- [ ] 현재 단계 타임라인이 있다.
- [ ] 입력/처리/출력 구조가 보인다.
- [ ] 촛불 장면에서 왜 지금 개입하는지 보인다.
- [ ] 보드/맵 장면에서 읽기 중 흔적이 읽기 후 산출물로 바뀌는 흐름이 보인다.

권장 타임라인:

> 읽기 시작 -> 읽기 중 -> 읽기 후 -> 다음 읽기 전

## 5. 리서치/검증 체크

### 5-1. Research Grounding

- [ ] 논문이 마지막에 몰려 있지 않다.
- [ ] 논문 이름보다 디자인적 사용이 보인다.
- [ ] 행동 신호 근거가 있다.
- [ ] 개입 타이밍 근거가 있다.
- [ ] 경쟁사 리서치와 노벨티가 연결된다.

권장 구조:

> 행동에서 인지를 읽는 근거  
> -> 브라우저에서 수집 가능한 신호  
> -> 마찰/흔적 해석  
> -> 촛불/보드/맵으로 반환

### 5-2. Validation / Next Test

- [ ] “AI가 정답을 맞췄다”가 검증으로 나오지 않는다.
- [ ] 촛불 수용성이 다음 테스트로 나온다.
- [ ] 보드/맵 납득도가 다음 테스트로 나온다.
- [ ] 아직 해소되지 않은 가설을 자진납세한다.
- [ ] 한계 뒤에 다음 제안이 붙는다.

권장 문장:

> Layer 2의 검증은 정확도보다 납득도에 가깝습니다.

## 6. 구현/비전 경계 체크

### 6-1. 인터랙션 디자이너 증거 자료

- [ ] Design Requirement가 보인다.
- [ ] Technical Diagram 또는 시스템 흐름이 보인다.
- [ ] Prototyping을 통해 판단이 바뀐 과정이 보인다.
- [ ] 요구 조건, 시스템 구조, 실제 화면이 서로 연결된다.

Layer 2 권장 구조:

> Requirements -> System -> Prototype

예시:

- Requirements: 읽기 흔적을 수집해야 한다 / 흐름을 방해하지 않아야 한다 / 나를 비추어야 한다.
- System: 읽기 행동 -> 신호 수집 -> 해석 -> 촛불/보드/맵 반환.
- Prototype: Reader, Candle, Board, Mental Model Map.

### 6-2. 구현됨

- [ ] 읽기 화면.
- [ ] 하이라이트/주석/동그라미/체류/되돌아읽기/스크롤 신호.
- [ ] 촛불.
- [ ] 보드 전환.
- [ ] Mental Model Map.
- [ ] 단일 세션 기반 리포트 또는 요약.

### 6-3. 비전/목업/다음 단계

- [ ] 다회독 거울.
- [ ] 재독 Diff.
- [ ] 관심사 크로스오버 맵.
- [ ] 완성된 시간대 추천.
- [ ] 대규모 어텐션 엔진.
- [ ] 퍼스널 에이전트 피드백 루프.

검수 질문:

- [ ] 비전 항목을 구현 완료처럼 말하지 않았는가?
- [ ] 구현 항목을 너무 축소해서 실제 만든 것이 약해 보이지 않는가?
- [ ] 30% 구현이라면 30% 구현으로 정직하게 말하고 전체 비전을 붙였는가?

## 7. Q&A Appendix 체크

### 필수 Appendix 주제

- [ ] Readwise와 차이.
- [ ] GPT/챗봇과 차이.
- [ ] 아이트래킹 없이 어떻게 막힘을 아는가.
- [ ] 마찰 계수의 정확성.
- [ ] 오래 머문 것의 모호성.
- [ ] 프라이버시.
- [ ] 촛불이 방해되지 않는가.
- [ ] 사용자 테스트/검증.
- [ ] 정답 없는 평가.
- [ ] 보드/멘탈맵이 단순 시각화가 아닌 이유.
- [ ] 다중세션/재독 거울 구현 경계.
- [ ] 마지막 비전이 과장되지 않는 이유.
- [ ] 임팩트: 연구/디자인/개발 커뮤니티에 줄 수 있는 것.

### Q&A 전략

- [ ] 본편에서 말하기 긴 내용은 Appendix로 보낸다.
- [ ] “질문 주시면 뒤 자료로 답하겠습니다”가 가능한 항목을 정한다.
- [ ] Q&A가 평가 기회라는 관점으로 준비한다.
- [ ] 자진납세 항목은 한계와 다음 제안을 같이 둔다.

## 8. Claude 초안 검수 질문

Claude가 만든 슬라이드를 받으면 아래만 빠르게 본다.

1. 첫 장이 프로젝트명/캐치프레이즈/키워드로 시작하는가?
2. 첫 1분 안에 “뭘 만들었는지”가 보이는가?

7. 보드 전환과 Mental Model Map이 `나를 비추기`의 핵심으로 보이는가?

9. 구현된 것과 비전/목업이 분리되어 있는가?
10. 마지막이 Thank you가 아니라 Recap/Vision/Question인가?
11. 평가기준 다섯 축이 모두 어딘가에 반영되어 있는가?
12. Q&A Appendix로 빠질 내용이 본편을 과하게 잡아먹지 않는가?
